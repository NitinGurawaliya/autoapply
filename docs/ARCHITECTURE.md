# ARCHITECTURE — SwipeApply

Read PRD.md first. This doc is the source of truth for structure, data model and flows. Update it in the same change when a decision changes.

## 1. Principles

- Production shape from day 1: Postgres (Neon), a job queue, a separate worker process, a storage interface (files in Postgres now, S3-compatible later), stateless web. One repo. Runs on one laptop for the demo and deploys as two services later (web + worker).
- Modular monolith: every module lives in `src/modules/<name>` and is imported by both the web app and the worker. Modules never import from `app/`.
- Nothing lives in local files. Companies, jobs, profiles, answers, applications, events → Postgres (Neon). Resumes and screenshots → the storage interface (`FileBlob` table in Postgres for the MVP; any S3-compatible bucket later). Config that changes per environment → env vars. `config/rules.json` is the only checked-in config, and it is loaded into memory at startup.
- Deterministic first, LLM second. Standard fields are mapped by code. The LLM runs only for resume parsing, unknown field labels, free-text answers and (optionally) match reasons.
- Governance is code (`modules/governance`), never only prompts. Every agent decision is an `ApplicationEvent`.

## 2. Stack

| Layer | Choice | Why |
|---|---|---|
| Web | Next.js 16 (App Router; `proxy.ts` instead of middleware), TypeScript strict | UI + API in one deployable |
| UI | Tailwind, shadcn/ui, Framer Motion, lucide-react | Fast, consistent |
| DB | Postgres on Neon via Prisma (any Postgres later) | Serverless Postgres, pooled + direct URLs |
| Queue | pg-boss (Postgres-backed job queue) | No Redis to run; same durability; swap to BullMQ later if needed |
| Worker | `src/worker/index.ts`, separate Node process (`npm run worker`) | Playwright never runs inside the web process |
| Browser | The stealthy Chrome (6.21), a visible window, driven by Playwright; Playwright's Chromium for tests and the mock form | Reliable fills, native file upload |
| Storage | `FileBlob` table in Postgres (`bytea`) behind `lib/storage.ts`; swap to S3/R2 later | No card, no extra vendor; same interface later |
| Auth | Auth.js (NextAuth v5) with Google provider + Prisma adapter | Users in our DB, no vendor lock-in |
| LLM | OpenAI Chat Completions, `gpt-4o-mini` (override with `OPENAI_MODEL`), JSON-only + Zod | The hackathon key on hand is OpenAI, not Anthropic |
| PDF text | `pdf-parse` | Simple |
| Push | `web-push` (Web Push protocol, VAPID) + `public/sw.js` | Reaches users with the app closed (owner's choice, 11 Oct); the protocol's encryption is not something to hand-roll |

## 4. Data model (Prisma, Postgres)

Auth.js adds `Account`, `Session`, `VerificationToken` via its Prisma adapter; keep them as generated. Sessions stay in the database (`lib/auth.ts`), but each request reads its session with one SQL join that also returns whether the user has a profile (`session.user.hasProfile`): the proxy routes on that flag and `getCurrentUser` returns the id, email and name from it, so signing in costs one query per request instead of four (Prisma's `include` was three round trips, plus a profile read in the proxy and a user read on the page). Measured 10 Oct on the dev server: `/answers` and `/account` 1.6–2.2 s → 0.8–1.1 s. Cookie (JWT) sessions were not chosen: the test scripts sign in with database sessions.

## 5. Canonical answer keys (`modules/answers/keys.ts`)

Identity: `first_name last_name full_name email phone city country linkedin github portfolio resume`
Work: `years_experience current_title current_company employment_type start_date preferred_location`
Sensitive (never AI-drafted; answer bank or ask user): `current_ctc expected_ctc salary_expectation notice_period work_authorization needs_sponsorship willing_to_relocate`
EEO (default "Decline to answer"): `gender race ethnicity veteran_status disability pronouns`
Misc: `how_heard` (default "Job board") · `cover_letter`, `free_text` (ai_draft allowed)
Permission: `accept_acknowledgements` (Yes/No, asked once; see 6.18)
Custom: `q_<12 hex>` = sha256 of the normalised label, for job-specific questions no canonical key covers (and for canonical fields whose value does not fit the form's options). Policy `bank_or_ask`, never AI-drafted; the answer is reused whenever the same label appears again.

Each key: `{key, type, synonyms: RegExp[], default?, policy: deterministic | bank_or_ask | ai_draft_ok | default_only}`.

## 6. Flows

### 6.1 Onboarding
1. `POST /api/profile/resume`: upload → `storage.put(`resumes/${userId}/resume.pdf`)` → `pdf-parse` → `llm.callJson(profileSchema)` → upsert Profile → seed Answer rows (identity/work keys, `source=resume`).
2. Confirm screen edits Profile and seeded answers (`PUT /api/profile`, `PUT /api/answers`). `/` and `/sign-in` still go to `/feed` once a Profile exists. `/onboarding/confirm` and `/onboarding/questions` stay reachable after that, so the candidate can correct the parse before the feed.
3. Questions screen writes `current_ctc expected_ctc notice_period employment_type preferred_location` (`source=user`), plus `work_authorization needs_sponsorship` if a non-India country is chosen.

### 6.2 Job ingest (worker job `ingest`, payload `{days}`)
1. Load `Company where active`. The list lives in `prisma/companies.ts` (`npm run seed`). Greenhouse companies are found with `scripts/discover-greenhouse.ts` (candidates in `scripts/greenhouse-candidates*.ts`): it checks each candidate's public board and counts its India-eligible open jobs, writes `docs/greenhouse-review*.csv`, and the owner approves which to keep and each `stage`. 10 Oct: 508 candidates, 113 on Greenhouse, 65 with India-eligible jobs (1,380 open: 1,172 in India, 208 remote); all 65 kept, 66 Greenhouse companies active (45 MNC, 19 mid-size, 2 startup). From Ashby only tech jobs open to India (in India or remote-India) are stored (`ingest.ts storedFromBoard`, 15 Oct): its boards are mostly US and non-tech roles; jobs stored before stay. Ashby companies come from discovery (`BOARDS`, Common Crawl index of `jobs.ashbyhq.com`), named from each board page's title.
2. Per company, call its fetcher:
   - Greenhouse `GET https://boards-api.greenhouse.io/v1/boards/{slug}/jobs?content=true` (date: `first_published` else `updated_at`)
   - Lever `GET https://api.lever.co/v0/postings/{slug}?mode=json` (date: `createdAt` ms)
   - Ashby `GET https://api.ashbyhq.com/posting-api/job-board/{slug}?includeCompensation=true` (date: `publishedAt`)
   - Pay (Phase M5, 18 Nov): from the boards' structured fields only, never from the description (`modules/jobs/salary.ts`): Ashby `compensation.summaryComponents` (its Salary component; on most postings, INR included), Lever `salaryRange` (1 of 1,568 postings on the largest board read). Greenhouse's public API returns `pay_input_ranges` empty on every board sampled (Stripe, Anthropic, Carvana, Coupang, Databricks, Figma, Airbnb, GitLab), so Greenhouse jobs show no pay. Stored as `Job.salaryMin/salaryMax/salaryCurrency/salaryPeriod`; a pay-only change writes only those columns (the job keeps its vector and verdicts).
   - Skills (Phase M2, M3): ingest stores `Job.skills`, the tech terms of a fixed ~210-term vocabulary the title or description names (`modules/jobs/skills.ts`: word boundaries, aliases, English-looking terms such as Go, Spring or Excel only inside a list of other tech terms). After embedding, `semantic.ts labelPendingSkills` asks the model which of those terms are required (`Job.skillsRequired`, `skillsHash` = the `contentHash` it read); it may only pick from the job's own list, and anything else it returns is dropped. ~855 input tokens a job (~$0.13 per 1,000 at gpt-4o-mini), `SKILL_LEVELS_PER_RUN` (default 2,000) per run, only the feed's pool (`modules/jobs/pool.ts poolSql`: open, an `APPLY_BOARDS` board, India-eligible, posted within `INGEST_DAYS`; Phase P, 19 Nov), newest first.
3. `normalize.ts` → Job; `functions.ts classifyTitle` → `function`, `track`, `seniority` (6.3); `tagging.ts` → `country`, `remoteType`, `experienceMin` (regex + city tables; LLM only with `llmTag=true`). Places match as whole words ("India" never matches "Indiana"); US is a US city, any state's name, or a two-letter state code after a comma ("Palo Alto, CA", not when the place is in Canada); India includes "IND" and more cities (10 Oct: 143 US jobs had been filed as Other). `scripts/backfill-job-features.ts` rewrites stored countries after a rule change. India eligibility (T77): `eligibility()` sets `Job.eligibility` from the location line, the board's offices (Greenhouse `offices`, e.g. "India Locations", "Bengaluru @ …, India") and, for a remote role that names no place, the description: `india` (an India place; when several places are listed, the India part decides whether it is remote), `remote_india` (remote and India, APAC/Asia, IST or anywhere/worldwide), `abroad` (any other place, or remote limited to other countries), `unknown` (nothing to go on, e.g. a bare "Remote" or "Hybrid", or a remote place we cannot read: when unsure, leave it out). The location line decides first; the offices only when it names no place; the description only for a bare "Remote" ("India", "IST", "work from anywhere"; not "global", which companies use for anything). Measured 10 Oct on all open jobs: Greenhouse 317 india, 18 remote_india, 2,307 abroad, 2 unknown; a spot check of 30 per bucket found one miss (fixed). The feed shows `india` and `remote_india` only (T80). `Job.firstSeenAt` records when ingest first saw a job. Greenhouse descriptions arrive HTML-escaped; `plainText` unescapes before and after removing tags (before 10 Oct the markup was stored as text). Check: `scripts/eligibility-test.ts`.
4. Keep `postedAt >= now - days`. Per company (T79): load the stored rows by `(source, externalId)`, `createMany` the new ones, rewrite only the ones whose `contentHash` changed, that moved company or that came back after closing (transactions of 50), then close the rest (6.16). 4 companies at a time, 300 ms between them, a 30 s timeout per request and one retry after 2 s; a company that still fails gets `Company.lastError` and is counted, the others go on. `Company.lastFetchedAt/lastFetchCount` are updated. One run at a time: a run starts by inserting an `IngestRun` row only when no unfinished run started within 2 hours, otherwise it logs and skips; the row gets the totals (companies, failed, fetched, created, updated, closed, deleted, new India-eligible) when it ends. Closed jobs nobody swiped or applied to are deleted 7 days after closing (30 until Phase M, M2). Measured 10 Oct on 116 companies (98 Greenhouse): first run 349 s, 14,521 listed, 4,792 new (549 India-eligible), 0 failed, jobs 3,561 → 8,353; second run 83 s, 0 written. Open Greenhouse jobs after it: 763 india, 77 remote_india, 6,345 abroad, 5 unknown. Check: `scripts/ingest-contract-test.ts`.
5. Scheduled: the worker registers a pg-boss cron on start (`src/worker/schedule.ts`): `INGEST_CRON` (default `0 */3 * * *`, UTC) with `{days: INGEST_DAYS}` (default 60, so an open job stays while it is listed; runs expire after 2 hours), stored in the database so several workers registering it is harmless, with `missed: "once"` so a run that came due while every worker was down happens once when one returns. The worker logs `ingest scheduled: ...` on start. Check: `scripts/schedule-smoke.ts`. Manual: `POST /api/jobs/ingest` and `npm run ingest -- --days 7`.
5b. **Tick mode (Phase M, M2, 9 Nov; `INGEST_MODE=tick`, default `run` until the switch).** Every company known to be on a board is watched, each at its own pace (`modules/jobs/cadence.ts`): `active` (an India-eligible job now or in the last 30 days) every 3 h, `open` (other openings) every 24 h, `empty` (no openings) every 3 days, `dead` (empty 90 days, 3 reads finding no board, or 8 failures in a row) every 30 days; the tier is recomputed after every read, a failure doubles the interval up to 7 days, every next read is jittered ±10% (`Company.tier`, `nextFetchAt`, `indiaOpen`, `lastIndiaAt`, `notFoundFetches`). Tick mode switches no company off. The `ingest-tick` cron (`INGEST_TICK_CRON`, every 5 min) sends each due company (most overdue first, up to `INGEST_TICK_BATCH`, 2,000) its own `ingest-company` job: one per company at a time (exclusive queue, `singletonKey`), grouped by board so at most `INGEST_PER_HOST` (4) reads of one board run at once across all workers (pg-boss `groupConcurrency`), `INGEST_CONCURRENCY` (8) per worker; then it starts the shared tail (5d) in the background, never two at once in one process. Each tick is one `IngestRun` (`tick_…`) whose counts the company reads add up. Switching `INGEST_MODE` unschedules the other mode. Cheap reads: Greenhouse's list without descriptions is hashed (`Company.listHash`) and an unchanged list skips the full read; Workday reads a posting's detail only when ingest does not hold it yet (`FetchedJob.listOnly`: a held posting is proven still listed by the list alone, reopened or moved but never rewritten). **India-only storage:** every board stores India-eligible jobs (`india`, `remote_india`; Ashby India tech only); the companies watched before Phase M on Greenhouse and Lever keep their jobs abroad (`Company.keepAbroad`, owner, 9 Nov). Run mode (`ingestJobs`) reads the same way and keeps its old switch-off rule. **Gentle boards and refused reads (owner, 18 Nov):** from 17 Nov Workday's Cloudflare answered this server's reads with its bot check (429, `cf-mitigated: challenge`) for 201 of 206 tenants after we read every tenant every 3 h, four postings at a time; we do not work around a bot check. A gentle board (`GENTLE_BOARDS`, Workday) is read 4 times less often (active every 12 h; dead unchanged), at most 3 of its companies sent a tick, one at a time across workers (pg-boss group tier `gentle`, concurrency 1), one request at a time with 1 s between them; once a posting's page is refused the rest are kept from the list. A refused read (a 429 or bot check, the fetcher's error says `refused`) is not retried at once, does not add to the failures in a row (no back-off, never dead) and keeps the company's tier. Checks: `scripts/cadence-test.ts`, `scripts/ingest-tick-test.ts` (fake board), `scripts/ingest-scale-smoke.ts` (the scheduler simulated at 20,000 companies: ~29,000 reads a day, 0.34/s; at most 5 min overdue in steady state; a cold start of all 20,000 read within 54 min; the per-board cap held). `scripts/ingest-tick-now.ts [--all]` reads the due companies once without the worker, then looks for missing logos; the tail is `scripts/after-ingest-now.ts` (5d).

5c. **On a GitHub Actions schedule (M21, owner, 18 Nov).** Ingest, discovery and the board day run whether or not a worker is up: `.github/workflows/jobs.yml` runs `scripts/ingest-tick-now.ts --limit 6000` every 3 hours (2 hours at most a run; ~30,800 companies need ~39,000 reads a day, 18 Nov) (`15 */3 * * *`, companies already due only), then `scripts/after-ingest-now.ts` as its own job (`after-ingest`, `needs: ingest`, run even when the read failed, 45 minutes at most; 5d), `scripts/discover-now.ts --boards <board>` daily at 01:30 UTC, one job per board (at most 4 at once, 150 minutes each), and `scripts/board-day.ts` at 23:30 UTC, each also by hand (`workflow_dispatch`). Secrets in the repository: `DATABASE_URL`, `DIRECT_URL`, `OPENAI_API_KEY`, and the `VAPID_*` keys and `APP_URL` for pushes. The worker then runs with `INGEST_MODE=off`, `DISCOVER_CRON=off` and `BOARD_DAY_CRON=off` (`worker/schedule.ts schedulePlan`): "off" unschedules that job for every worker, since pg-boss keeps the schedules in the database, so every worker must run with the same switches. Freshness is then the Actions interval (3 hours, and GitHub may start a scheduled run late), not the tick's 5 minutes. Check: `scripts/schedule-plan-test.ts`.
5d. **One after-ingest tail and job reading (Phase P, P1, 19 Nov; docs/relevance/TDD.md 4.1.1–4.1.3).** Every ingest path ends in `modules/jobs/after-ingest.ts afterIngest({ deadlineMs })`: embed new jobs → label the skills of the feed's pool → read pool jobs → warm the feeds when anything was embedded, labelled or read → delete old closed jobs (at most hourly per process). Each step fails alone and stops at the deadline; the next call resumes. Callers: the worker's tick after its sends, in the background (`AFTER_INGEST_TICK_MS`, 8 min); `scripts/after-ingest-now.ts` as the workflow's `after-ingest` job (`AFTER_INGEST_RUN_MS`, 40 min); run mode's `ingestJobs`, whose handler no longer warms on its own. Logos stay with the callers. **Job reading** (`modules/jobs/reading.ts`): the model reads the title and the first 6,000 description characters, 10 jobs a call, and returns the job's field (`roleFamily`: a track or `non_tech`), `kind` (`employee | intern | contract | gig | task`), `flags` (`paid_task`, `commission_only`), a one-line summary, evidence lines and up to 4 requirement lines. Code keeps only quoted lines found in the posting (HTML entities decoded; case, spacing, quotes and dashes normalised); a kind other than employee or a flag without a kept line is dropped; a field without one is kept only when the title's own classification (`classifyTitle`) says the same, the title then being its evidence; a value outside the enums reads as null. The trigger `job_reading_stale` clears `readingCurrent` on insert and when the title or description value really changes (ingest rewrites both on any change, so a moved location keeps the reading). A reader claims jobs (`readClaimedUntil`, 10 min, `FOR UPDATE SKIP LOCKED`), writes only while `md5(title || chr(10) || description)` still equals what it read, and after 3 failed attempts waits 24 h. ### 6.5 Apply runner (worker handler, stateless, re-runnable)
```
load application, job, profile, answers, rules
governance.check('start')                       → block → status blocked (+ event)
if profile.isTest and adapter.source != 'mock'  → block (rule test_profile_mock_only)
browser.open(job.applyUrl)                      (the stealthy Chrome window)
adapter = pickAdapter(job.applyUrl, job.source)   # source wins: Greenhouse listings often link to company careers sites
browser.open(adapter.formUrl?(job) ?? job.applyUrl)
fields  = adapter.inspect(page)                 → FormField[] {selector,label,type,required,options}
keys    = fieldMapper.map(fields)               → synonyms → FieldMappingCache → LLM → cache
values, pending = valueResolver.resolve(fields, keys, profile, answers, rules)
   # order per field: user's answer to this exact label (q_ key) → acknowledgement (6.18) → answer bank → profile → key default → ask
   # option fields: value must match one of the form's options (exact, unique prefix, or a single numeric range);
   # EEO keys pick the form's own "decline" option; otherwise → ask
if pending.length: save pendingQuestions, status needs_input (attempt unchanged), event ask_user, close, return
adapter.fill(page, values)                      → event per field
adapter.uploadFile?(page, resume, bytes) ?? setInputFiles   (temp file deleted in finally)
screenshot → storage.put(`screenshots/${appId}/${attempt}.jpg`)   (JPEG q72 since 16 Oct; older ones .png)
governance.check('submit')                      → block if fails
adapter.submit(page, {requestCode}); wait for confirmation (URL change / "thank you" text / form gone)
   # requestCode: when the ATS emails a one-time code mid-submit (Greenhouse "security code"), the runner sets
   # needs_input with pending [{key:"security_code"}] and KEEPS THE BROWSER OPEN, polling Application.verificationCode
   # every 2 s for up to 10 min. This is the one exception to "never hold a browser while waiting": the code is
   # bound to that browser session, so a re-run would trigger a new code. Up to 3 tries; timeout → failed (no retry).
status submitted, submittedAt, event submit
on error: attempt < 2 and not NoRetryError → event retry, re-enqueue; else status failed, error, event error
   # NoRetryError: thrown after the submit click (no confirmation, form rejected, CAPTCHA). Retrying could send a duplicate application.
finally: close browser
```
Needs-input resume: `POST /api/applications/:id/answers` upserts Answer rows (`source=user`) → `enqueueApply(id)`; the run starts again from the URL.
Security code: the same route, for key `security_code`, writes `verificationCode` and sets `filling` (the waiting worker picks it up); it is never stored in the answer bank. If the application has been waiting longer than 10 min (worker gone), it is re-queued instead.

### 6.6 Adapter interface (`modules/apply/adapter.ts`)
```ts
export interface AtsAdapter {
  source: 'greenhouse' | 'lever' | 'ashby' | 'mock';
  matches(url: string): boolean;
  formUrl?(job: { applyUrl; externalId; companySlug }): string;   // the real form when the listing is not the form
  inspect(page: Page): Promise<FormField[]>;
  uploadFile?(page: Page, value: ResolvedValue, bytes: Uint8Array): Promise<() => Promise<void>>;
  fill(page: Page, values: ResolvedValue[]): Promise<FilledField[]>;
  nextStep?(page: Page): Promise<FormField[] | null>; // more questions: an answer revealed them, or Next opened a page (§6.22)
  submit(page: Page): Promise<SubmitResult>;   // {confirmed: boolean, evidence: string}
}
```
`adapters/common.ts`: `fillText`, `selectOption`, `pickComboboxOption(labelText)`, `uploadFile(bytes, name)`, `waitForConfirmation`.

Ashby (`adapters/ashby.ts`): form address is the posting's `/application` page. Every question is an outermost `[data-field-path]` block (checkbox groups, which include most acknowledgements, do not carry the `.ashby-application-form-field-entry` class, so the class is never used to find questions); option text comes from the box's `label[for]`; a Yes/No pair counts as answered when a button is pressed (its hidden checkbox stays unticked for No); the adapter reads each block's one control (text, textarea, Yes/No button pair, radios, checkbox group, select, location type-ahead, date picker, file) and gives the mapper a `hintKey` for name, email, location and resume. Attaching a resume does not auto-fill (that is a separate button we never press). Date pickers need a real date: a value that is not one (for example "Immediate") becomes a question for the user, and a plain number is read as days from now. Submit is the "Submit Application" button, and **a person presses it** (human handoff, 21 Oct), unless `ASHBY_AUTO_SUBMIT=1` (below). The form runs Google reCAPTCHA when Submit is pressed: a Submit the worker pressed itself was stopped before anything was sent (1 of 23 through; a traced run showed the challenge with no submit request sent), while a person's Submit in the handoff window went through 7 of 7 from the same machine and applicant. See "Human handoff" below.

All adapters share `adapters/common.ts`: `assertJobOpen` turns a missing form on a closed posting into "This job is no longer open" (job feeds keep listing taken-down jobs), and `toDatePickerText` parses dates. Check: `scripts/adapters-test.ts` (offline) and `scripts/ats-smoke.ts` (live dry run).

Lever (`adapters/lever.ts`): form URL is the posting's `/apply` page. Fields are found by name (`name`, `email`, `phone`, `org`, `location`, `urls[...]`, `cards[...]`), and the adapter gives the mapper a `hintKey` for the fixed ones. `uploadFirst: true`: Lever reads the resume on upload and pre-fills fields ("Analyzing resume..." then "Success!"), so the runner uploads, waits for that, then fills so our values win. Location is a type-ahead whose suggestion is clicked (an optional location with no match is skipped; a required one asks the user for another search word). The optional demographic survey is left blank. Submit is `#hcaptchaSubmitBtn`; every Lever form has hCaptcha, and a visible challenge ends the run with "submit it yourself". Lever is switched off (not in `APPLY_BOARDS`); no real Lever form has reached `submitted` yet (TASKS T18). Check: `scripts/ats-smoke.ts --user <id suffix> <jobId>` (dry run for any adapter; `--user` is required so it never runs as the wrong profile).

Keka (`adapters/keka.ts`): form URL is `{slug}.keka.com/careers/applyjob/{id}`; fields come from Keka's public form JSON and are found on the page by id, and the resume goes in through the page's own uploader. Every form has an image CAPTCHA, read by `captcha/ai.ts` and typed by the worker, which then presses Apply Now itself in a visible window. Keka answers in seconds, and the run never waits on a person (3 Nov): its success page confirms; its error page, the red box at the top (its duplicate check: already applied, one job at a time) or a field's message ends the run at once as `failed`, with Keka's words as the reason and a screenshot; "Invalid captcha" (`CaptchaRejectedError`) closes the window and fills the form again from the start with a new CAPTCHA, up to 3 times in a row (runner.ts, not counted as failed attempts), then fails.

Greenhouse (`adapters/greenhouse.ts`): always opens the hosted form `https://job-boards[.eu].greenhouse.io/embed/job_app?for={slug}&token={externalId}`, which works for boards.greenhouse.io, job-boards.greenhouse.io and company careers sites alike. Inspects text/tel/number/textarea/select/checkbox/radio/file inputs and react-select comboboxes. Checkboxes and radios are read per `name`: a fieldset with several boxes is one `checkbox-group` question (legend = question, box labels = options), a one-box fieldset (an "Acknowledge" consent) is one `checkbox` named by its legend and is always asked, never ticked for the candidate; groups are filled by ticking the box whose label fits the answer. A `number` input takes only a number (`valueResolver`: "30 days" → 30; "Immediate" → asked if required, skipped if not). Before Submit, `missingRequired` lists required questions still empty (text, select, react-select still on its placeholder, groups with nothing ticked; hidden ones ignored) and stops the run with their names, so nothing is sent with holes. Check: `scripts/greenhouse-form-test.ts`. Combobox options are read from the input's own `aria-controls` listbox (the phone widget keeps a second country listbox). Comboboxes with no options or more than 50 (location, school) are search fields: the answer is typed and matched against live results. Waits for `networkidle` before uploading (the uploader script loads late), attaches the resume through the "Attach" file chooser and waits for the file-name chip. Confirmation: `/confirmation` URL or "thank you for applying" text. A visible reCAPTCHA challenge fails the run with "open the form and submit it yourself".

### 6.7 Concurrency

`worker/index.ts` registers `apply` with pg-boss `localConcurrency = APPLY_CONCURRENCY` (default 3, clamped 1–24). Since T100 (18 Oct) runs share one Chromium per worker process (`browser.ts`; a second, headed one for the handoff, which Greenhouse also uses since 25 Oct: `AtsAdapter.window`, a real Chrome window where the worker has a screen, the worker pressing Submit itself; headless at the same 1280x800 page in Docker. 25 Oct, 5 Greenhouse jobs in the visible window: all sent, none asked for the emailed security code), each run in its own incognito context, so cookies and storage are never shared between users and two runs of one user simply get two contexts. Measured, 8 runs at once on Windows: 23 processes and 0.97 GB private memory, against 78 processes and 2.35 GB as 8 browsers. The limit is RAM and how many simultaneous submissions one IP tolerates. A user's cookies and local storage are saved through `lib/storage.ts` as `browser-state/<userId>.json` (owned by the user, so account deletion erases it; never served by `/api/files`) when a run closes and restored when the next opens, on any worker; two runs of one user at once: the last to close wins; over 512 KB only the cookies are kept. A shared browser that dies is relaunched by the next run, and one is replaced after `BROWSER_RECYCLE_AFTER` (default 200) runs once its last run closes. The form opens only for inspect, fill and submit: when the job's questions are already cached on its row (`questionsCached`), they are answered first and the browser opens after; only when they still have to be fetched does the form load meanwhile. A run waiting for a security code holds its slot (and context) for up to 10 minutes. `BROWSER_PROFILE_ROOT` now only holds the worker's pid lock; per-user profile folders from before T100 are removed by the reaper as their users are deleted. Check: `scripts/profile-isolation-smoke.ts`.

### 6.8 Cancel and one submit at a time

`Application.status = cancelled` stops a run: every runner status write goes through `setApp`, which refuses to overwrite `cancelled` and throws `CancelledError`; the code-wait loop checks it every 2 s, and a cancelled application that reaches the worker again returns at once. `npx tsx scripts/clear-queue.ts` cancels every in-flight application and every `created/retry/active` apply job (history is kept). Submit and code entry run one application per user at a time (`withSubmitLock` in `modules/apply/submitLock.ts`: one `SubmitLock` row per user, taken with one atomic upsert, a 2-minute lease renewed every 20 s while the holder works, so it holds across several worker processes and a dead holder is taken over when its lease runs out; waiters poll every 2 s, so it is mutual exclusion, not first-come-first-served): two forms waiting on codes at once put two emails in one inbox with no way to tell which is which. Filling and uploading stay parallel. Apply jobs are sent with `expireInSeconds: 3600` and `retryLimit: 0`: a form can legitimately wait behind another application's code, and a blind pg-boss re-run of a form that may already have been submitted could apply twice. The runner refreshes `Application.heartbeatAt` every 30 s while it works. Every worker runs `reapStaleRuns` (`src/worker/reaper.ts`) each minute: an application whose apply job is still `active` in pg-boss but whose heartbeat is older than 3 minutes belongs to a dead worker, so it is marked `failed` ("The worker stopped while running this application. Retry it."), its queue job is cancelled and its submit lock freed. Applications waiting for answers have no active job and are never reaped. Check: `scripts/queue-smoke.ts` (includes a second real process).

### 6.9 Duplicate and company guards

`modules/governance/history.ts` holds the swipe-time history: a role is `roleKey(companyId, normalised title)`, so the same role listed under two ids is one role. Rules in `config/rules.json`: `no_duplicate_role` (an application that was submitted or is in flight blocks a second one; failed, blocked and cancelled ones do not count) and `max_per_company_per_week` (default 3, counted over 7 days). Both run in the `swipe_right` check before the score and daily-cap rules, so a blocked swipe ends `blocked` with the rule name. The feed (and so the feed pre-scan) also leaves out companies that already have `max_per_company_per_week` applications in the last 7 days (`feedHistory`): a swipe there would be blocked, and the pre-scan would ask questions for a job that cannot be sent. Every count these rules use (queue, today's total, this company this week, duplicate role) is read inside the swipe's per-user advisory lock (`historyFor(…, tx)` in `lifecycle.ts swipeRight`), so a burst of swipes cannot pass a cap together: before 10 Oct six swipes at once all saw the same daily total and 24 got through a cap of 20. The feed hides roles already applied to, and the feed and applications pages show today's count against `max_applications_per_day`. Since 16 Oct the cap counts applications started today except blocked ones (`dailyUsage`; a blocked one never ran), and "sent today" on screen counts only submitted ones (`dailySent`). `pending_verification` (an application whose Submit may have gone out unconfirmed) counts like a submitted one for these rules. Account deletion (`modules/account deleteAccount`) also removes `FeedGap`, `FeedScan` and `JobJudgement`, which have no foreign key to the user. The eval's tables (`EvalPool`, `FeedLabel`, `EvalJudgement`) go with the profile by cascade. Check: `scripts/guards-test.ts`.

### 6.10 Cancel and retry from the UI

`POST /api/applications/:id/cancel` (owner only; allowed while queued, inspecting, filling or needs_input) marks the application cancelled, cancels its queue job, frees its submit lock and writes a `cancel` event. `POST /api/applications/:id/retry` (owner only; allowed from failed or cancelled) re-runs the same swipe-time rules as a new swipe (`no_duplicate_role`, `max_per_company_per_week`, `min_match_score`, daily cap, supported board), then resets the attempt count and queues it again; a blocked retry returns 403 with the rule name and leaves the application unchanged. Both live in `modules/apply/lifecycle.ts`, which web routes import directly (importing the `apply` index would pull Playwright into the web bundle). The buttons are `components/application-actions.tsx`, on the list rows and the detail page; cancelling an application that has a browser open asks first. The live status endpoints are `no-store` and clients fetch with `cache: "no-store"`. Check: `scripts/lifecycle-smoke.ts` (works with or without a worker running).

### 6.12 Multi-user safety

Every API route resolves the signed-in user and scopes its queries by `userId`; another user's application, file or answer is answered with 404, and signed-out calls get 401. Limits: free-text inputs are length-bounded (answers 2000; question text up to 5000, stored shortened to 1000 because real form labels can run past 700 characters; profile fields per `profileSchema`; resume text is cut, not rejected); batches are capped; `/api/jobs/ingest` is operator-only (`ADMIN_EMAILS`, 1 to 60 days, 3 per hour); resume uploads are 10 per user per hour (`lib/rate-limit.ts`, a counted-rows limiter in Postgres, atomic and shared by every web instance, pruned by the worker). The mock form and its endpoint return 404 in production unless `ENABLE_MOCK_FORM=1`. The worker opens only allow-listed hosts for the job's ATS (`modules/apply/urls.ts`, https only, no userinfo or odd ports; the mock form only on this app's own host), otherwise the application is blocked with `unsafe_form_url`. Fairness: `max_in_flight_per_user` (default 25) caps one user's queued and running applications so they cannot fill the shared worker. All responses carry nosniff, frame-deny, referrer and permissions headers; `/api/files` responses are private, no-store and sandboxed. A user can download their data (`GET /api/account/export`) and erase everything (`POST /api/account/delete`, exact phrase required): the user row cascades profile, answers, swipes, applications and events, and `modules/account` also removes stored files, locks, rate counters and queue jobs and stops anything running; their saved browser cookies go with their stored files (the worker also deletes any pre-T100 browser-profile folders of users that no longer exist). Not yet: a strict Content-Security-Policy. Check: `scripts/security-test.ts`.

### 6.15 Learning from results

`modules/jobs/results.ts` counts, per company and board and across every user, how applications ended (submitted, failed) and how many asked for an emailed security code (from the `ask_user` events); cancelled runs and the mock form are ignored, and only counts leave the module. After 3 finished runs `judge` gives a hint and a ranking nudge: failing 60% or more is "Often fails to submit" (-4); asking for a code half the time or more is "Usually needs an emailed code" (-2); 2 or more clean submits with low failure and code rates is +3. The nudge only reorders the feed; the match score the user sees is unchanged, and the hint appears as a tag on the card. Numbers are cached for a minute. Check: `scripts/results-test.ts`.

### 6.16 Closed jobs, browser slots and one worker per machine

- A run that ends "no longer open" is checked against the company's own public board (`modules/jobs/listing.ts listingState`). Listed means the page failed to load, so it is retried and worded "The form did not load". Gone sets `Job.closedAt`. Unknown (board unreachable) keeps the old behaviour. Page text alone never closes a job.
- A browser profile that dies while opening ("has been closed", Singleton lock) moves on to the next slot instead of failing the run.
- A second worker on the same machine refuses to start (`worker/single.ts`, pid file in `BROWSER_PROFILE_ROOT`): before T100 two workers shared profile folders and knocked each other's browsers over. Since T100 nothing is shared on disk, so the lock is only a guard against starting the same worker twice by mistake; to use a bigger machine, raise `APPLY_CONCURRENCY`.

### 6.17 Adapter hardening and many swipes at once

- **One swipe path.** `lifecycle.swipeRight` is the only place a right swipe is handled (the API route and the tests call it). Inside one transaction it takes a per-user advisory lock, recounts running and queued applications, and records the swipe and application, so a burst of swipes cannot overshoot `max_in_flight_per_user` (25). A swipe refused for a full queue is not recorded at all (HTTP 429, the deck puts the card back); it is not a refusal of the job.
- **Place in line.** `/api/applications` returns `ahead` for queued applications (queued applications created earlier, over all users) and the list shows it.

- **Duplicate-submit guard** (`modules/apply/outcome.ts decideAfterError`). Each adapter calls `markAttempted` right before Submit (handoff: at the first request to Ashby once the form is ready), which writes a `submit_attempt` event. Before that, the old retry rules apply. - **`pending_verification`** shows under "Needs you" as "Check your email". The user says whether the employer's confirmation came (`POST /api/applications/[id]/verify`, `lifecycle.ts resolveVerification`): sent becomes `submitted` (dated when the outcome became uncertain), not sent becomes `failed`, after which Retry is allowed.
- **Diagnostics** (`adapters/ashbyDiagnostics.ts`, `ASHBY_DIAGNOSTICS=1` only, off by default): log lines of Ashby request paths with ids masked, GraphQL operation names, statuses, allowlisted error codes, fixed categories and page-state booleans; never a body, server or console message, personal data or token. Ashby's submit operation is `ApiSubmitSingleApplicationFormAction`.
- Checks: `scripts/submit-guard-test.ts`, `scripts/ashby-diagnostics-test.ts`.

- **Adapters share `adapters/common.ts`.** `dismissOverlays` declines cookie banners before filling and before Submit; `inField` names the field in any fill error; `friendlyError` turns Playwright timeouts into sentences; `firstVisible` finds the Submit button under any of its names. Greenhouse, Lever and Ashby all use them.
- **Before Submit.** Lever reads the browser's own `:invalid` fields; Ashby reads required questions that are still empty. Either stops the run with the question names, so a half-empty form is never sent.
- **Unsupported questions.** A required Ashby question of a kind the agent cannot answer stops the run before anything is filled, naming the question; an optional one is skipped.
- **Failures leave evidence.** A failed run saves a full-page screenshot and the site's own error lines (`screenshots/<id>/fail-<n>.jpg`, event `diagnostic`). A sent run also saves the board's confirmation page (`sent-<n>.jpg`), shown on the application page.
- **Retries wait.** A retry starts 20 seconds times the attempt number after the failure.
- `rateLimit` takes a per-key advisory lock, so parallel calls cannot slip past the limit.

### 6.18 Acknowledgements (privacy, truthfulness, arbitration, routine consents)

Most forms require a box such as "I have read the privacy notice", "my answers are true and complete" or "I acknowledge the arbitration agreement" and reject the application without it. Since 1 Nov (owner: the obvious consent questions go through on their own) the same rule covers routine consents: interviews being recorded or transcribed (an AI notetaker, "Interview Recording Consent"), the company's AI policy for interviews, and declarations that the details given are correct; a choice picks its one affirmative option ("Yes, I consent to be recorded", "I consent"), never "I do not consent". The Ashby reader leaves out only the SMS and WhatsApp opt-ins inside the phone question, so a consent question of its own is read (UiPath's recording consent had stopped runs). `modules/apply/acknowledgement.ts` `acknowledgementValue(field)` recognises a **required** field as one (a single checkbox, a group with exactly one box, or a choice with exactly one affirmative option) by its wording, and never counts marketing opt-ins or certifications of facts (work authorization, sponsorship, age, record, past employment). These are a legal choice, not a fact, so the agent does not decide alone: the resolver asks once for the standing permission `accept_acknowledgements` (one question per run, however many boxes). With Yes, every adapter ticks them from then on, recorded as the user's answer under that key; with No, each acknowledgement is asked on its own; an earlier answer to the exact question always wins. The user can change it on `/answers`. Check: `scripts/acknowledgement-test.ts`.

Field mapping guard (10 Oct): a key the model picks, now or from `FieldMappingCache`, must fit the field: never one of the agent's own keys (`accept_acknowledgements`, `accept_ai_essays`, `essay_best_project`, `sponsorship_outside_home`), and never a text fact for a tick box. A Coinbase dry run had mapped "I understand that Coinbase may use AI tools…" to the essay permission and the work-history "Current role" tick box to the job title; work-history "Start date month / year" no longer match `start_date`. Notices worded "I understand that…" are acknowledgements. `scripts/ats-smoke.ts` dry runs now resolve with `resolveForm`, the chain a real run uses.

First real run after the 10 Oct changes (Stripe, Software Engineer New Grad, nitin): asked 5 facts before opening the form, then submitted after the emailed security code. It found three bugs, fixed the same day: (1) the stale-run reaper (`worker/reaper.ts`) compared the application's old heartbeat, from the attempt that asked the questions, instead of the newer of that and the new queue job's start, so a run resumed more than 3 minutes after the ask was failed 2 s after starting ("The worker stopped while running this application"); it now uses `GREATEST(heartbeatAt, started_on)`; (2) `refersToTheJob` counted every "country where/in which" as the job's country, so "the country where you currently reside" never reused the user's answer; only "the country where you will be working" (with "this/the job", "you are applying") points at the job now; (3) Greenhouse's demographic-data consent box (`gdpr_demographic_data_consent_given`) says it is optional but blocks the submission once the demographic questions are answered (always, with "Decline to self-identify"); the adapter reads it as a required acknowledgement, ticked under the standing permission.

### 6.19 Answer memory (retrieve, then verify)

Every saved answer's question is embedded so a new wording can find the user's past questions that mean the same (Phase F, T49-T57). Built so far (T51): pgvector in the same Neon database (`CREATE EXTENSION vector`, migration `answer_memory`); `Answer.embedding vector(1536)` plus `Answer.embeddedHash` (md5 of the wording it was computed for) and `Answer.context` (the job an answer was given for: company, title, location, country; set by `POST /api/applications/:id/answers`, null for onboarding and the answers page); `LabelEmbedding` caches one embedding per distinct wording for all users (wordings are not personal). `modules/answers/memory.ts` (raw SQL, the vector column is invisible to Prisma): `labelVectors` (cache first, then `lib/llm.ts embed()`, `text-embedding-3-small`), `ensureEmbeddings(userId)` (re-embeds answers whose wording is new or changed, so a save stays one query), and `recall(userId, labels)` (the user's 5 closest past questions per label with cosine score >= 0.54). Recall only proposes candidates: in the T49 experiment on 197 real wordings, true paraphrases scored as low as 0.599 while look-alike traps scored as high as 0.834 ("work from our US office" vs "London office"), so no threshold is safe and a verify step decides (T52). Answers saved before T51 have no context and are never reused for company-, city- or country-specific questions. Checks: `scripts/embedding-experiment.ts`, `scripts/memory-smoke.ts`, `scripts/backfill-embeddings.ts`, and the replay scoreboard `scripts/replay-questions.ts`.

Retrieve, then verify (T52): when the resolver leaves questions pending, `modules/apply/recall.ts` `answerFromMemory` recalls candidates and makes ONE verify call per form (`callJson`; model `OPENAI_VERIFY_MODEL`, default the normal model: `gpt-4o` was measured and reused less without fewer mistakes). The model proposes; code decides: the candidate must be one it was offered; the detectors in `modules/answers/concepts.ts` (residence, work authorization, sponsorship, relocation, office attendance, worked-at, company relationship, compensation, notice period, EEO) cannot be overridden to "general" and both questions must be the same kind; these risky kinds reuse only the user's own answers; kinds with a parameter need the same country / place / company on both sides, written in the question or in the job / answer context (`grounded`); different parts of one thing never share an answer (day/month/year, start/end, degree/major, address/city/state/zip, first/last name); a yes/no answer never fills an open question and an open answer never fills a yes/no one. Accepted answers enter `resolveValues` with source `matched` and a `basis` ("your answer to …"), kept on the filled field and its fill event. In the resolver, a risky question with a parameter is never answered from a global saved answer, nor from the same wording when that wording points at the job ("this role", "our office", "the country where the job is located"): only a verified memory answer counts, otherwise it asks. Replay over 237 real questions: before, 26 % answered without asking with 7 wrong sensitive answers; now 34 % with 0. Most remaining disagreements are the user's own conflicting answers (different addresses on different forms, "enrolled" vs "not returning"), to be settled on the Answers page (T56). Checks: `scripts/recall-test.ts`, `scripts/recall-smoke.ts` (mock form end to end).

Option mapping (T53): the resolver reports answers it had but could not place on a field's options (`unfit`); the runner sends the still-pending ones to `modules/apply/optionMap.ts` `mapToOptions` (one call per form, cached) and resolves again. The model may only pick one of the options shown, or none; sensitive and EEO answers may only be re-worded, never changed ("30 days" → "1 month", "Yes, I am authorized" → "Authorized", "12 LPA" → "10-15 LPA"; "60 days" with no such option stays asked). The resolver uses a mapping only when the option is really on the form; the field keeps its source and gets the basis `your answer "…", as this form's option`. Checks: `scripts/option-map-test.ts`, `scripts/option-map-smoke.ts` (mock form end to end). Numbers in ranges are placed by code first (`numericRange` in `valueResolver.ts`, in the resolver and before the model): a number with a unit fits the one range of the same unit that holds it ("12 LPA" → "10-15 LPA", "3 years" → "3-5 years"; a bare number fits ranges in years); a number on the edge of two ranges goes to the model. The prompt allows "Other" only for a non-sensitive answer that names something the options do not (10 Oct: the model had stopped mapping both cases).

Derivation (T54): after memory, `modules/apply/derive.ts` `deriveAnswers` works out what the profile and resume prove, source `derived` with the evidence as basis: residence ("Do you reside in the US or Canada?") from the profile's country (not when the question mixes in relocation, or asks about a smaller place in the user's own country); "worked at <company>?" from the resume's employers (not for "any government entity"); "N years of experience in X?" is No when total experience is under N and Yes only when the resume's dated roles involving X add up to N (dates normalised in code; the model may only say which existing roles involve X, the arithmetic is code). It never touches pay, notice period, work authorization, sponsorship, citizenship, relocation, office or EEO questions. Citizenship ("U.S. person", green card) is its own risky kind, never matched to work authorization. Replay: 46 % answered without asking, 0 wrong sensitive answers, 0 derivations on a forbidden kind; the 12 derived answers that contradict a saved answer are listed for review (profiles in India with saved "Yes, I live in the UK / worked at Snowflake"). Checks: `scripts/derive-test.ts`.

Essay drafts (T55, product decision): `modules/apply/essay.ts`. Open questions ("why this role / why us", "best project you've built", "tell us about…") are drafted from the resume and the job only. Since 30 Oct (owner) no permission question comes first (it was friction for something every candidate wants); a user who answered No to `accept_ai_essays` before, or sets it on the Answers page, writes their essays themselves; a draft that names an organisation, school or product absent from both is dropped and the question asked. "Best project" is drafted once and saved as `essay_best_project` (`ai_draft`, editable on the Answers page) and reused; "why this company" is drafted per application and only an answer given for the same company is ever reused (never the global free-text answer). At most `max_ai_drafts_per_application` (3) drafts per application, now enforced; the rest are asked. Checks: `scripts/essay-test.ts`, `scripts/essay-smoke.ts` (mock end to end).

Decisions (10 Oct): conflicting saved answers are not reviewed; the newest wins (the verify step prefers the most recently saved candidate, and sees save times to the minute). For a question about one country, code enforces it over all the user's answers saved for that country and place, not only the closest wordings recall offered (`newestSamePlace` in `recall.ts`; a dry run reused an older "Yes, authorized in the US" over a newer "No"). Years-of-experience questions are always derived when the resume settles them (no switch). Essay drafts must also be numerically grounded: every number in a draft must appear in the resume or the job, otherwise the draft is dropped and the question asked.

Ask before the run (T56): `modules/apply/resolveForm.ts` is the one answering chain (exact / canonical → memory → derived → essays → option mapping), used by the live run, the check before the run and the feed pre-scan. `modules/apply/questions.ts` reads a job's questions without a browser: Greenhouse's public `…/jobs/{id}?questions=true` (labels match the hosted form; cached on `Job.questions` for a day), Workable's public form JSON `apply.workable.com/api/v1/jobs/{shortcode}/form` (the same fields the Workable adapter fills, M12; cached the same way) and a fixed list for the mock form; other boards return null. Forms whose questions cannot be read ask mid-run as before. `POST /api/applications/:id/answers` also re-queues every other application of the user waiting on any of the same questions (one answer releases them all; one waiting for an emailed code is left alone). "Fill your gaps": the `prescan` queue job (`modules/apply/prescan.ts`, at most once per user per 10 minutes, started from the feed when the last scan is over 30 minutes old and after answers are saved) resolves the questions of the user's top 20 feed jobs and stores `FeedScan` (jobs answerable in full) and `FeedGap` (each missing fact and how many jobs it blocks). Questions about the job's country are grouped by country under one plain wording ("Are you legally authorized to work in the United States?") and saved with that country (`FeedGap.context` → `Answer.context`), so one answer serves every job there in any wording. `/gaps` shows coverage and the gaps; `POST /api/gaps` saves an answer with the gap's context. Checks: `scripts/precheck-smoke.ts` (mock end to end), `scripts/gaps-test.ts` (real Greenhouse question lists, read only).

Answer what the data settles (30 Oct, owner: "make the agent smart, do not ask the obvious"; never a made-up fact): `modules/apply/infer.ts` `inferAnswers`, run by `resolveForm` after the memory and derived steps on every question still open and every one only a default filled, in two model passes per form. Pass 1, from saved answers: each question with its own closest saved wordings (`recall`, 8 at score >= 0.45, wider than the memory step) and the user's standing facts (canonical keys: expected CTC, notice period, start date...; their short wordings sit far from the many ways forms ask, "Expected CTC" scored under 0.3 against "What are your salary expectations?"); the model reuses the same fact in other words or re-formats it ("Expected CTC 18" → "18 LPA"), and a second narrow call confirms each reuse is the same question (it rejects "experience with IAM" from "experience with Kafka"). Pass 2, from the profile alone (city, country, links, years, roles, degrees, skills; never email or phone) for what is still open: what it states or plainly implies (a finished degree for "over 18?", the city for "Which city are you based in?"). The passes are separate on purpose: in one call the model linked look-alikes (a zip code answered "no", an address line with how the user heard of the job) and cited profile fields as cover. Code keeps the hard rules: evidence must exist (an answer copied word for word is credited to its source, never a yes / no); the shape fits (`differentParts`, yes / no vs open, as recall.ts); every number is in the evidence or is the form's option; "null" / "N/A" are no answer; sensitive keys and risky kinds only from the user's own answers with a yes / no saying what theirs says, country kinds compared by code (named in the question, else the job's country; named in the saved question, else the job it was answered for) since the old grounding matched India's code "in" to the word "in", place and company kinds the grounded-parameter check with real places only (not "onsite"); from the profile only an open "where do you live" among risky kinds, and never a "No" (a resume's silence proves nothing); EEO, essays, acknowledgements and id-like labels are left out. Malformed model items are skipped, questions the model leaves out are asked once more. Replay (4 users, 136 questions, plain text fields, no job): answered without asking 48 → 62; remaining wrong answers seen are ambiguous labels ("Colonist Profile", "End date year" outside its section) and the profile's location against older typed ones. Checks: `scripts/infer-test.ts` (real model, a throwaway user), `scripts/replay-questions.ts` (the step's answers tagged `+infer`). The Ashby adapter also reads a picker's fixed choices from Ashby's form description, so its options are matched or shown to the user.

Profile facts and contradictions (11 Oct): for profile-backed keys (city, country, phone, links, current company and title) the confirmed profile beats an older saved answer (a "City = Greater Delhi Area" from 8 Oct had kept beating the profile's Bangalore). Greenhouse location pickers retry simpler search words ("Greater Delhi Area" → "Delhi"). A saved yes / no answer that contradicts what the resume, the profile or the standing answers prove is not reused (`resolveForm`): the proven answer goes in, source `derived`, with both in the basis. `scripts/contradictions.ts [--fix]` lists such saved answers per profile and corrects them (13 fixed on 11 Oct). The onboarding questions screen asks the three standing answers (citizenship, open to moving abroad, sponsorship outside the home country) for everyone, replacing the old global "authorized to work there" answer.

Jobs abroad (10 Oct, owner): questions about another country are answered from the profile or from standing answers asked once, never guessed (`modules/apply/places.ts`, `abroad.ts`, `derive.ts`). `places.ts` reads which countries a question names (countries incl. sanctioned ones, regions, Canadian provinces, US states and cities, foreign cities; "us" counts as the country only in capitals) and whether it is outside the home country (else the job's country). ### 6.20 Signed-in sources: Naukri and LinkedIn (Phase K, owner, 29 Oct)

### 6.21 The stealthy Chrome: every run's browser (M12, owner, 17 Nov)

Decision: every browser the worker opens, on every board and for every kind of run (main, handoff, window), is a real Google Chrome started by SeleniumBase in UC + CDP mode, with Playwright attached to its DevTools port. Adapters are unchanged: they get the same `context` and `page`. Why: Workable's Turnstile failed the Playwright Chrome even for a person's tick (11 Nov, 0 sent); in the stealthy Chrome Turnstile stayed silent and the worker's own Submit sent 7 of 7 Workable forms, with Greenhouse, Keka and Ashby also sent by the worker.
- **Parts.** `scripts/seleniumbase_cdp_launcher.py <url> <port>` starts Chrome (`SB(uc=True, headed=True)`, `--remote-debugging-port`, `activate_cdp_mode`), prints `READY <port>` and waits on stdin; `QUIT` or EOF kills its own process tree (uc_driver, Chrome) and exits without SeleniumBase's teardown, which left one `uc_driver.exe` per launch. `modules/apply/real-browser.ts openStealthyBrowser` picks a free port, spawns it, `connectOverCDP`, restores the owner's saved cookies, and its `close` quits Chrome over CDP before stopping the launcher. `browser.ts openBrowser` calls it first and saves state after, as before.
- **No silent fallback.** If the stealthy Chrome cannot start the run fails and is retried; the Playwright browser opens only with `STEALTHY_FALLBACK=1`. `STEALTHY_BROWSER=0` turns the stealthy Chrome off. `STEALTHY_PYTHON`, `STEALTHY_READY_MS` (90 s), `SELENIUM_CDP_PORT` (free port by default).
- **Needs a screen and Python.** The Chrome is headed, so a worker runs it only where `canShowWindow()`; Python with `seleniumbase` must be installed there (the first launch fetches a matching uc_driver). This is why Workable stays in `HANDOFF_BOARDS` though the worker presses its Submit: that list also routes to a worker with a screen, and a challenge still goes to the person.
- **Evidence.** Each launch, attach, failure and close is appended at once to `stealthy-browser.log` (`STEALTHY_LOG`) in the worker's folder; which browser a run used is read there, never from how a window looks (17 Nov: a Docker worker on the same queue opened Playwright Chrome windows that were taken for this one).
- **Not solved by it.** Lever's hCaptcha shows a puzzle in any browser (off, T94). SmartRecruiters' DataDome (M7) stays quiet at one run at a time (12 real submits on 17 Nov, none challenged); back-to-back runs from one IP bring its slider, which goes to a person (§6.22).

### 6.22 SmartRecruiters: multi-page forms in components (M7, 17 Nov)

Decision: SmartRecruiters' Easy Apply (`oneclick-ui`) is applied to like any board, in `APPLY_BOARDS` and `HANDOFF_BOARDS` (`ENABLE_SMARTRECRUITERS=0` turns it off). `adapters/smartrecruiters.ts`.
- **Pages and revealed questions: `nextStep`.** After `fill` the runner calls `adapter.nextStep(page)` until it returns nothing (at most 10 rounds); each set it returns is resolved, asked (needs_input) or filled like page 1. SmartRecruiters returns first any unread question an answer revealed ("Yes" to English → spoken and written levels), then, once none is left, presses Next and returns the screening page. Ashby (18 Nov) reads the form again after each fill and returns the questions that appeared (Commure: the type of sponsorship, shown after sponsorship Yes); a single page, so null once nothing new shows.
- **Every field is an `spl-*` component in an open shadow DOM.** Each is tagged `data-sa-q=<n>` as read; its text comes from its `label` attribute, its `[slot=label-content]`, or its aria-label, never invented. Read: input, textarea, number field (unit in the label, "(INR)"), phone, single and multi-select search boxes (long lists scrolled to the end; filled by typing to filter, then the option clicked and checked), radio and checkbox groups (text in `label`), checkbox, resume dropzone. A required component it cannot read stops the run by name; nothing is skipped in silence.

- **DataDome.** On opening, a challenge waits 2 minutes for a person in the window, then hands the run over (`BotCheckError`); it is never solved by the agent. After Submit, a reply of 200 from `/application` is the proof; when nothing is sent, the message names the questions the form marks.
- **Checks.** `scripts/ats-smoke.ts` (`--fill-pending`, `--draft-essays`) reads every page and blocks the application POST.

## 8. LLM gateway (`lib/llm.ts`)

`callJson<T>(schema, system, user, {cacheKey?})`: JSON-only system prompt, strip fences, parse, Zod-validate, one retry. Calls OpenAI `POST /v1/chat/completions` with `response_format: json_object`. Cache: in-memory per process + `FieldMappingCache` for field labels. Logs tokens/latency. One model for the MVP (`gpt-4o-mini`). Switched off Anthropic because that key was never issued; `OPENAI_API_KEY` is the one in `.env`. `lib/claude.ts` (1 Nov) is the same helper for Claude: `callClaude(system, user)` returns text, `callClaudeJson(schema, system, user, {cacheKey?})` validated JSON; text only, `claude-opus-5-5` by default (`ANTHROPIC_MODEL`), server-side fallback on a refusal. It needs `ANTHROPIC_API_KEY`; nothing calls it yet.

## 9. Storage (`lib/storage.ts`)

Resume upload and replace (18 Oct): the PDF reader gets a copy of the bytes (pdf.js empties the array it is handed; from 12 to 18 Oct every resume was stored as 0 bytes and no form could upload it), an empty file is never stored, and a run stops before opening a browser when the stored resume is missing or empty. "Replace resume" (Account) re-runs onboarding: the person's details (name, email, phone, city, country, links) stay and only a blank one is filled; skills, roles, education, title, years and the resume text come from the new resume; the user's own answers stay; the AI "best project" draft is dropped and drafted again; the review screen shows what changed (`parseResume.ts mergeResumeProfile`, `saveParsedResume`). Check: `scripts/resume-test.ts`. Runs (18 Oct): non-Ashby forms open while their published questions are worked out (closed again if the run stops to ask); fill events go in one write; the resume is read once a run.

Interface: `put(key, bytes, contentType, userId?)`, `get(key)`, `url(key)`. MVP implementation: `FileBlob` table in Postgres. Keys: `resumes/{userId}/resume.pdf`, `screenshots/{appId}/{attempt}.jpg` (and `sent-`/`fail-` variants; `.png` before 16 Oct). `url(key)` points at `GET /api/files/{key}`, which streams the bytes only to the owning user. The worker writes the resume bytes to a temp file for Playwright upload and deletes it in `finally`. Later: an `S3Storage` class with the same interface (R2/S3) selected by env; callers never change.

## 10. Mock Greenhouse form (`/mock/greenhouse`)

Same ids as Greenhouse where easy (`#first_name #last_name #email #phone #resume`), plus a custom combobox (`#how_heard`), a notice-period text (`#notice_period`), a work-authorization select (`#work_authorization`), a free-text question (`#free_text`) and an EEO section (`#gender #race #veteran_status #disability`, default "Decline to answer"). `POST /api/mock/submit` stores the payload in `MockSubmission` (resume file name only, not the bytes). `/mock/submissions` lists those payloads. `/mock` is outside the auth proxy: the worker browser has no session.
